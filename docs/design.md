# Дизайн MVP: EDSM System Search

## Цель

Самостоятельный HTTP-сервис, который находит центральную звёздную систему по имени, а затем возвращает системы из каталога EDSM в заданном евклидовом радиусе в 3D.

## Технологии

- Rust stable
- Axum + Tokio — HTTP-сервис
- rusqlite — SQLite, сборка с feature `bundled`
- Serde / serde_json — потоковая десериализация
- flate2 — gzip
- clap — команды запуска и импорта
- tracing — логи
- thiserror — ошибки

Не используем PostgreSQL, Kiddo, FST, rkyv и самописный формат хранения.

## Хранилище

Одна SQLite база `systems.db`.

Основная таблица `systems`:
- `edsm_id INTEGER PRIMARY KEY`
- `id64 INTEGER NULL`
- `name TEXT NOT NULL`
- `name_norm TEXT NOT NULL`
- `x/y/z REAL NOT NULL`
- `updated_at TEXT NULL`

Индексы:
- B-tree `systems(name_norm, edsm_id)`
- B-tree по `id64`
- виртуальная таблица `systems_rtree` с измерениями X/Y/Z.

R*Tree используется только для получения кандидатов по bounding box. SQLite R*Tree хранит границы как float32, поэтому окончательная проверка расстояния выполняется по координатам REAL из основной таблицы с вычислением в f64. R*Tree и основная таблица синхронизируются SQL-триггерами в рамках одной транзакции.

## Поиск центра

1. Нормализовать входное имя: trim и ASCII lowercase.
2. Искать точное равенство `name_norm`.
3. Если точного совпадения нет, последовательно удалять последний разделённый пробелом компонент.
4. На каждом укороченном уровне искать имена с этим префиксом.
5. При нескольких кандидатах выбирать первый по `name_norm ASC, edsm_id ASC`.
6. Если кандидатов нет ни на одном уровне — вернуть 404 с понятным кодом ошибки.

Для LIKE-поиска экранировать `%`, `_` и `\\`. Нормализация не должна менять исходное имя, которое возвращается клиенту.

## Пространственный поиск

Для центра (x0, y0, z0) и радиуса r:
- запросить R*Tree по пересечению с bounding box [x0-r, x0+r] × [y0-r, y0+r] × [z0-r, z0+r];
- присоединить кандидатов к основной таблице;
- отфильтровать по точному условию dx² + dy² + dz² <= r²;
- вернуть расстояние в световых годах;
- порядок результата: distance ASC, name_norm ASC, edsm_id ASC.

Радиус должен быть конечным положительным числом и ограничиваться конфигурационным максимумом сервиса. Центральная система включается в результат при радиусе > 0; это поведение фиксируется тестом.

## Импорт

Импортёр читает верхнеуровневый JSON-массив потоково через serde_json Visitor/SeqAccess; запрещено десериализовать весь дамп в Vec.

Записи применяются пакетами ограниченного размера в транзакциях. Повторный импорт идемпотентен: UPSERT по edsm_id. Триггеры обновляют R*Tree. Некорректные записи (нет обязательных полей, нечисловые/неfinite координаты) пропускаются и учитываются в статистике импорта; ошибка структуры верхнего уровня завершает импорт с ошибкой.

Полный дамп используется для первоначального наполнения и периодической сверки. Скользящий 7-дневный дамп используется для регулярного обновления. Отсутствие записи в 7-дневном дампе никогда не трактуется как удаление. В MVP импортёр получает локальный путь к файлу; расписание и скачивание дампов остаются задачей оператора (cron/systemd timer).

Не требуется держать весь импорт в одной гигантской транзакции. При аварии уже применённые пакеты остаются валидными, а повторный импорт безопасен.

## HTTP API

- `GET /health` — liveness и проверка доступности базы.
- `GET /search?center=Sol&radius=2500` — поиск центра и соседей.

Успешный ответ включает выбранный центр, радиус, количество результатов и массив систем с координатами и расстоянием. Ошибки имеют стабильные машинные коды: invalid_request, center_not_found, database_error.

Ограничение максимального радиуса задаётся конфигурацией; значение по умолчанию — 10 000 ly. Значение должно быть настраиваемым переменной окружения.

## Память и конкуренция

- SQLite WAL.
- Ограниченный SQLite page cache на каждое соединение.
- Не использовать неограниченный mmap.
- rusqlite — синхронный API; операции базы выполнять вне async executor (spawn_blocking).
- Импорт и HTTP-сервис не должны разделять одно соединение SQLite. Они используют отдельные соединения к одной локальной базе.
- WAL рассчитан на процессы на одном хосте; базу не размещать на сетевой файловой системе.

## Не входит в MVP

- Полнотекстовый поиск и fuzzy matching.
- Сопоставление систем по координатам/ID вместо имени.
- Автоматическое скачивание дампов и планировщик внутри сервиса.
- Удаление записей на основании отсутствия в 7-дневном дампе.
- Авторизация, распределённое хранилище, несколько серверов.
- Планетарные данные и фильтры по характеристикам планет.

## Известные ограничения

EDSM — неполный каталог игровых систем. Результат означает «найдено в локальном каталоге EDSM», а не «все существующие системы в игре».
