# Перепроектирование: Spansh API вместо локального каталога EDSM

Статус: проектирование принято; реализация выполняется в ветке refactor/spansh-api-search.

## Цели

- Полностью отказаться от локального каталога систем, SQLite, R*Tree, EDSM dump importer и фоновой синхронизации.
- Не скачивать и не хранить галактические дампы.
- Получать центральную систему и её координаты через Spansh.
- Искать непосредственно небесные тела в заданном радиусе от координат центра через Spansh Bodies Search.
- Сохранить семантику поиска центра: точное имя имеет приоритет; если совпадения нет, последовательно отбрасывать завершающие компоненты имени и брать первое совпадение.
- Не обещать полноту сверх того, что Spansh возвращает: count может быть ограничен 10 000; поиск должен обрабатывать страницы и указывать возможную усечённость.

## Целевая архитектура

HTTP request -> Axum validation -> SearchService -> SpanshClient.resolve_system(name) -> SpanshClient.search_bodies(reference_coords, filters, page) -> bounded page collector -> normalization/deduplication -> response.

### Слои

1. API (api.rs): HTTP DTO, валидация, статус-коды, health endpoint без зависимости от локальной БД.
2. Application (service.rs): разрешение центра, сбор страниц, лимиты, дедупликация, преобразование ответа.
3. Spansh gateway (spansh/client.rs): HTTP, таймауты, user-agent, обработка статусов и JSON.
4. Spansh DTO (spansh/models.rs): типизированные структуры с терпимостью к неизвестным полям.
5. Domain (domain.rs): координаты, центральная система, планета, поисковые фильтры и итоговые результаты.

## Контракты Spansh

### Разрешение имени

Первичный запрос: GET /api/search/systems?q={urlencoded_name}. Выбирать точное совпадение по results[].name. Если точного совпадения нет — выполнять fallback, удаляя последние компоненты названия. Для префиксного fallback допустим GET /api/systems/field_values/system_names?q={prefix}; из min_max[] брать запись с детерминированным первым совпадением. Центральная запись должна содержать id64, name, x, y, z.

### Поиск тел

POST /api/bodies/search, JSON:
- filters: пользовательские фильтры; обязательно distance: {min: "0", max: "<radius>"}.
- sort: [{ "distance": { "direction": "asc" } }].
- size: 1..500 (первоначально 100 или 250; конфигурируемо).
- page: 0-based.
- reference_coords: координаты разрешённой центральной системы.

Для получения всех страниц отправлять тот же запрос с возрастающим page. search_reference/recall endpoint можно использовать позже как оптимизацию, но базовая реализация не должна зависеть от срока жизни search reference.

### Поля результата body

Минимальные поля: id64, body_id, name, subtype, system_name, system_id64, system_x/y/z, distance, distance_to_arrival, is_landable, gravity, surface_temperature, surface_pressure, atmosphere, terraforming_state, volcanism_type, materials, signals, genuses, updated_at.

Все ID64 хранить как u64 (не f64 и не JS Number); поля, отсутствующие в отдельных записях, делать optional. Неизвестные поля игнорировать.

## Ограничения и устойчивость

- Не более одного активного Spansh поиска на процесс в первой версии; semaphore защищает upstream от всплесков.
- Общий deadline на поиск и отдельные connect/read timeout.
- Повторять только сетевые ошибки, 429 и 5xx; backoff ограничен небольшим числом попыток.
- Не повторять 4xx (кроме 429), ошибки валидации и некорректные фильтры.
- Максимальный радиус, максимальное число страниц и максимальное число тел — конфигурируемые ограничения.
- Не возвращать частичный результат как полный: если достигнут лимит страниц/записей, выставлять truncated=true и count_capped=true при необходимости.
- Небольшой in-memory TTL cache допустим как оптимизация; correctness не должна от него зависеть. На первом этапе кэш не обязателен.
- /health проверяет доступность процесса, не делает дорогой запрос к Spansh. Отдельный upstream readiness endpoint может проверять Spansh с коротким timeout.
- Никаких локальных файлов данных, persistent volumes или фоновых импортов.

## Стратегия тестирования

### Unit tests (без сети)
- URL encoding имён систем, пустой/пробельный ввод.
- Точное совпадение выигрывает у префиксных совпадений.
- Fallback удаляет ровно последний компонент за итерацию; первый подходящий результат выбирается детерминированно.
- ID64 больше 2^53 сохраняется без потери точности.
- DTO переживает отсутствующие optional поля и неизвестные поля.
- Body request содержит reference_coords, distance, sort и 0-based page; page size ограничен 500.
- Дедупликация одинакового тела не удаляет разные тела одной системы.
- Сортировка результатов детерминирована по distance, system name/id64, body_id.
- Радиус должен быть finite, > 0 и <= max radius.

### Mock HTTP integration tests (локальный mock server)
- Счастливый путь: resolve system -> 2 body pages -> объединённый ответ.
- exact lookup 0 результатов -> fallback к усечённому имени.
- 400/404 от Spansh -> корректная ошибка API, не 500 с утечкой внутренностей.
- 429/503 -> ограниченный retry, затем понятная ошибка.
- timeout/connection reset -> ограниченный retry.
- пустая последняя страница, отсутствие results, count=0.
- count > лимита и максимальная страница -> truncated выставлен.
- upstream возвращает дубликаты на соседних страницах.
- неизвестные JSON поля не ломают десериализацию.

### API tests
- GET /health не открывает и не создаёт БД.
- Валидный поиск возвращает центральную систему, планеты и метаданные полноты.
- Пустое имя, NaN/Infinity, отрицательный/слишком большой радиус отклоняются.
- Ограничение конкурентных upstream запросов.
- upstream недоступен -> 502/503, а не пустой успешный ответ.

### Live smoke tests (ignored / manual)
- Разрешить известную систему (Sol) и проверить координаты.
- Поиск 10–20 тел в радиусе 25 LY от Sol.
- Запросить 2 страницы и сравнить count/from/results.
- Проверить большой ID64 и реальную форму body records.
- Не запускать массовый полный галактический поиск в CI.
